# Registry vs Fork: как правильно строить дизайн-систему

Когда ты решаешь создать свою дизайн-систему на базе shadcn/ui, есть два пути. Разберём их простыми словами.

---

## Что такое Fork?

**Fork** — это когда ты копируешь весь репозиторий shadcn/ui себе и начинаешь менять код напрямую.

Представь: ты взял чужую квартиру, сделал ремонт под себя, и теперь живёшь там. Проблема в том, что когда в оригинальной квартире обновили проводку или починили крышу — тебе придётся делать это самому заново.

### Как выглядит Fork

```
my-design-system/           ← Копия всего shadcn/ui
├── components/
│   ├── button.tsx          ← Твои изменения прямо в файле
│   ├── card.tsx
│   └── ...
```

### Проблемы Fork-подхода

| Проблема | Что это значит |
|----------|----------------|
| **Сложные обновления** | Когда shadcn выпускает новую версию, тебе нужно вручную переносить изменения в свой код |
| **Конфликты** | Твои изменения могут конфликтовать с обновлениями оригинала |
| **Дублирование работы** | Исправления багов в shadcn не попадают к тебе автоматически |
| **Разрыв с экосистемой** | Ты теряешь совместимость с плагинами и дополнениями |

---

## Что такое Registry?

**Registry** — это «магазин компонентов». Вместо копирования всего кода, ты подключаешь компоненты как конструктор LEGO.

Представь: ты не копируешь квартиру, а строишь свою из стандартных блоков. Когда производитель улучшает блоки — ты просто заказываешь новые.

### Как выглядит Registry

```
my-design-system/
├── registry/
│   ├── bases/              ← Базовые компоненты (из shadcn)
│   │   └── base/
│   │       └── ui/
│   │           ├── button.tsx
│   │           └── card.tsx
│   └── styles/             ← ТВОИ стили поверх базы
│       └── style-nova.css
```

### Ключевая идея

> Компоненты остаются стандартными, а **стили — твои**.

Ты не меняешь код кнопки. Ты меняешь её внешний вид через CSS.

---

## Архитектура Registry: 5 слоёв

Registry работает как конструктор из 5 слоёв. Каждый слой можно менять независимо:

```
┌─────────────────────────────────────────┐
│  5. ИКОНКИ      Lucide, Hugeicons       │
├─────────────────────────────────────────┤
│  4. ШРИФТ       Inter, Figtree          │
├─────────────────────────────────────────┤
│  3. ТЕМА        Цветовая палитра        │
├─────────────────────────────────────────┤
│  2. СТИЛЬ       Vega, Nova, Maia...     │
├─────────────────────────────────────────┤
│  1. БАЗА        Radix UI, Base UI       │
└─────────────────────────────────────────┘
```

### Что означает каждый слой

| Слой | Что это | Пример |
|------|---------|--------|
| **База** | Фундамент компонентов (логика, доступность) | Radix UI или Base UI |
| **Стиль** | Отступы, скругления, типографика | Nova (компактный), Maia (мягкий) |
| **Тема** | Цветовая палитра | Neutral, Rose, Blue |
| **Шрифт** | Типографика | Inter, Figtree, JetBrains Mono |
| **Иконки** | Библиотека иконок | Lucide, Hugeicons |

---

## Сравнение: Fork vs Registry

| Критерий | Fork | Registry |
|----------|------|----------|
| **Обновления** | Ручное слияние кода | Обновление одной командой |
| **Твои изменения** | Смешаны с базовым кодом | Отделены в слой стилей |
| **Риск сломать** | Высокий | Низкий |
| **Время на поддержку** | Много | Мало |
| **Совместимость** | Теряется со временем | Сохраняется |

---

## Как работает обратная совместимость

### При Fork-подходе

```
shadcn v1.0 → Твой fork → shadcn v2.0
                ↓
        😰 Ручное слияние
        😰 Конфликты
        😰 Потеря твоих изменений
```

### При Registry-подходе

```
shadcn v1.0 ──────────────→ shadcn v2.0
     ↓                           ↓
  Твои стили                  Твои стили
  (отдельно)                  (остаются)
```

Твои стили живут **отдельно** от кода компонентов. Когда обновляется база — стили продолжают работать.

---

## Как обновлять дизайн-систему

### Шаг 1: Обновление базовых компонентов

```bash
# Одна команда обновляет все компоненты
npx shadcn@latest add button --overwrite
```

### Шаг 2: Проверка стилей

После обновления проверь, что твои CSS-стили всё ещё работают. Обычно работают, потому что:

- Компоненты используют стандартные CSS-классы (`cn-button`, `cn-card`)
- Твои стили привязаны к этим классам, а не к внутренней структуре

### Шаг 3: Адаптация (если нужно)

Если shadcn изменил структуру компонента:

```css
/* Было */
.cn-button-content { ... }

/* Стало (если переименовали) */
.cn-button-label { ... }
```

Такие изменения редки и документируются в changelog.

## Практический пример

Допустим, ты хочешь сделать все кнопки с большим скруглением.

### Fork-подход (плохо)

Открываешь `button.tsx`, ищешь классы, меняешь:

```tsx
// Было
className="rounded-md"

// Твои изменения
className="rounded-full"
```

Проблема: при обновлении shadcn твои изменения могут потеряться.

### Registry-подход (хорошо)

Создаёшь свой файл стилей:

```css
/* registry/styles/style-my-brand.css */

.style-my-brand {
  .cn-button {
    @apply rounded-full;
  }
}
```

Компонент `button.tsx` остаётся стандартным. Твой стиль применяется поверх.

---

## Когда всё-таки нужен Fork?

Fork оправдан, если:

- Ты меняешь **логику** компонентов, а не внешний вид
- Тебе нужны компоненты, которых нет в shadcn
- Ты готов поддерживать свою версию самостоятельно

Для большинства дизайн-систем Registry — лучший выбор.

---

## Итого

| Если ты хочешь... | Используй |
|-------------------|-----------|
| Свои цвета и стили | Registry ✓ |
| Свои отступы и типографику | Registry ✓ |
| Получать обновления | Registry ✓ |
| Изменить логику компонентов | Fork |
| Добавить уникальные компоненты | Registry + свои файлы |

**Registry** = безопасный способ кастомизации с сохранением обновлений.

**Fork** = полный контроль, но полная ответственность за поддержку.
